# Contributing

Thanks for helping. This document covers the branching model, how to make a change, and how releases
are cut. For build and test commands, see [Development](README.md#development) in the README.

## Branching model: git-flow

This repository follows [git-flow](https://nvie.com/posts/a-successful-git-branching-model/).

| Branch | Purpose | Branches from | Merges into |
|---|---|---|---|
| `main` | Released code only. Every commit on `main` is a tagged release. | n/a | n/a |
| `develop` | Integration branch for the next release. **The default branch: open PRs here.** | `main` (once) | n/a |
| `feature/<name>` | New features and non-urgent changes | `develop` | `develop` |
| `bugfix/<name>` | Fixes for unreleased code on `develop` | `develop` | `develop` |
| `release/<version>` | Stabilizing a release: version bumps, docs, last fixes | `develop` | `main` **and** `develop` |
| `hotfix/<version>` | Urgent fixes to a released version | `main` | `main` **and** `develop` |

Release tags are `v<version>`, e.g. `v0.2.0`, and are placed on `main`.

### With the git-flow tool (optional)

The [git-flow extension](https://github.com/petervanderdoes/gitflow-avh) works with this repository.
After cloning, initialize it with the repository's branch names:

```sh
git flow init -d   # accepts the defaults: main, develop, feature/, bugfix/, release/, hotfix/, support/, tag prefix "v"
```

Then, for example: `git flow feature start my-change` … `git flow feature finish my-change`.

### Without the tool

Plain git works the same way. The rule that matters: **feature, bugfix, release and hotfix branches are
merged with `--no-ff`**, so each one stays visible as a unit in history.

## Making a change

1. Branch from `develop`:
   ```sh
   git switch develop && git pull
   git switch -c feature/short-description
   ```
2. Make the change, with tests (see below).
3. Run the checks:
   ```sh
   cargo test -p tauri-plugin-reactive
   cargo test -p tauri-plugin-reactive --features typegen
   cargo clippy --workspace --all-targets
   npm test && npm run typecheck
   ```
   If you touched runtime behavior, also run the end-to-end self-test for at least one framework
   (`cd examples && npm run lib && npm run selftest:react`).
4. Push the branch and open a pull request **into `develop`**.

### Expectations for changes

- **Bug fixes come with a regression test** that fails without the fix.
- **Concurrency and lifecycle fixes** (subscriptions, sinks, reloads, window teardown) should be
  demonstrated: show that the test fails when the fix is removed.
- **Public API changes update the README** in the same PR. The README documents every public API.
- **New commands** need a permission: add the command to `COMMANDS` in `build.rs`, and decide whether it
  belongs in `permissions/default.toml`. The generated files under `permissions/autogenerated/` are
  committed.
- Keep changes focused. Unrelated refactors belong in their own branch.

## Releases

1. Branch from `develop`:
   ```sh
   git switch develop && git pull
   git switch -c release/0.2.0
   ```
2. Bump the version in **both** `Cargo.toml` and `package.json` (they are released together and share
   a version number), and update the README if needed.
3. Merge into `main`, tag, and merge back into `develop`:
   ```sh
   git switch main && git merge --no-ff release/0.2.0
   git tag -a v0.2.0 -m "v0.2.0"
   git switch develop && git merge --no-ff release/0.2.0
   git branch -d release/0.2.0
   git push origin main develop --follow-tags
   ```
4. Publish from the tagged commit on `main`: `cargo publish`, then `npm publish`.

### Hotfixes

Same as a release, but branch from `main` as `hotfix/<version>` (bumping the patch version), then merge
into `main` (tag it) and `develop`.
